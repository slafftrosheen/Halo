## Forms and routes must expose these distinctions

- **Edit scope:** “This occurrence” and “Entire series” must be explicit, carrying the immutable occurrence identity and expected record version. There is no this-and-future operation in the current foundation; do not present one as supported. Changing a series with exceptions currently supports rejection or explicit reset, not automatic exception preservation. A reset must explain that moved/cancelled/completed occurrence changes are removed, and Cancel must retain both the form draft and stored series.
- **Task hierarchy:** Show remaining subtasks and why completion/deletion is unavailable. Current `validateParent` requires an active parent for a child save/restore, so editing or reopening a child under a completed parent needs an explicit parent-reopen route or a deliberately revised rule. Do not make “reopen” appear enabled when the owner must reject it. Recurring occurrence completion/reopening must not mark the whole series completed.
- **Delete versus cancel:** Deletion is a versioned soft delete with a version-bound Undo token. Cancelling leaves a visible record with a different status. Deleting a parent with any live child is blocked. Expose a real move/delete-children path and preserve the exact deletion version; a stale snackbar must not restore a later deletion. Undo restores the record, while delivery restoration must separately reconcile and show its current outcome.
- **Timer states:** Running, paused, elapsed/awaiting delivery, stopped and actually notified are distinct. Current `stopTimer` writes COMPLETED even when stopped early; presentation must not imply that time elapsed or an alert fired. Show remaining time from the timer owner, not a decrementing UI counter. Pause cancels scheduling through the same outbox; resume uses a fresh schedule identity and current owner version. A paused timer stays paused across restart/reboot.
- **After reboot or clock change:** Same-boot timer duration correctly uses elapsed time; reboot falls back to wall time. Explain the actual resulting deadline, especially after a wall-clock change. Define missed/expired behavior before connecting notifications: the planner currently returns an immediate timer delivery at zero remaining, while already-past ordinary notification triggers are skipped. “Saved” cannot imply that a past occurrence will still alert.
- **Saved versus scheduled:** Saving succeeds even if the scheduling enqueue callback fails; the durable outbox is intentionally retained. Forms should show the saved record plus “scheduling pending” until a matching delivery receipt exists. Exact, approximate, notifications blocked, failed, missed and fired states need distinct readable copy and recovery actions. Old-version receipts are history, not proof that the current edited schedule is active.
- **Date/recurrence clarity:** Show zone/follow-device selection, exact next occurrence, end date versus count, and chosen behavior for DST gaps/overlaps. Monthly dates such as the 31st currently skip invalid months; leap-day recurrence skips non-leap years. An all-day end is an exclusive midnight boundary internally; the form must not imply an extra included day. Display only recurrence options the owner/importer supports.
- **ICS import:** Present valid records and per-item issues before committing. Unsupported recurrence is not silently approximated. Cancel imports nothing; accepted items retain source identity/attribution and their actual import count. An imported source URL is attribution, not authorization to fetch it in Local.

## Required owner-level acceptance cases before rendered review

1. Moved recurring task completion and per-occurrence Undo preserve title/time and siblings; both manual and typed commands use the same operation.
2. Cancelled/completed/moved floating occurrences retain their logical identity after zone change and restart. Fixed-zone events keep their chosen-zone time.
3. Future alarm deletion/Undo restores exactly one current schedule; stale callbacks from the deleted revision cannot fire or overwrite its result.
4. Series edit with exceptions rejects without changing storage; explicit reset is atomic and accurately reports the affected exception count. A concurrent edit invalidates the preview.
5. Parent/subtask completion, deletion, restore and reopen have consistent eligibility, including recurring parents and completed ancestors.
6. Timer create → pause → restart → resume → reboot → elapsed/stop works with delayed callbacks, same-boot wall-clock changes, and expired fallback. No stale callback fires after pause or cancellation.
7. Save/outbox enqueue failure shows saved/pending, retries from durable intent, and rejects stale acknowledgement. Current receipt rendering waits for the current record version; permission refusal exposes approximate/blocked behavior truthfully.
8. DST-invalid intervals, recurrence boundary dates and date-range limits fail visibly rather than producing missing/inverted agenda rows; successful empty is distinguishable from query failure.
9. Timestamp precision and capacity recovery cases in OF07/OF08 pass after actual database/codec round trips.

The current tests provide useful examples of DST, moved events, ordinary delete/Undo, outbox versioning and non-recurring parent completion. They were read, not executed in this review, and do not yet cover the eight findings above. Matching implementation evidence is required before any closure or score.
