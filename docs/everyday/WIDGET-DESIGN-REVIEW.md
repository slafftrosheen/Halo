## Visual contract

Use one calm Halo card: **20dp outer radius**, 12–16dp internal padding, 8dp row spacing, with `surfaceContainerLow` background, `onSurface` content, `onSurfaceVariant` metadata and `outlineVariant` boundary. A selected/control surface uses `primaryContainer/onPrimaryContainer`; actionable emphasis and the static orb use `primary`. Error meaning remains `error`, never the chosen accent. High contrast uses the same stronger foreground/outline mapping as `HaloTheme`; translucency is disabled there. External launcher cards use an opaque surface so unknown wallpaper does not determine text contrast.

Use the actual static `nearbyOrb`/brand ring once per widget header where space permits. It is decorative when the card already has a named open action; a separately clickable orb must have a distinct purpose and a full target. Do not repeat or animate the orb in each dashboard row. Preserve the in-app shared Zone 5 orb and shell; no additional global navigation strip or permanent card-edit toolbar.

Proposed text hierarchy: 18sp heading, 16sp content/action, 14sp attribution/status, with a larger clock value only where measured bounds support it. Font sizes are semantic starting sizes, not auto-shrink targets. At 200%, long locales or a narrow host, remove whole secondary rows before reducing usable text/targets. Keep the content identity, essential state and one clear open path. A headline may be an explicitly bounded preview; its publisher, stale/error state and complete reader route must remain. Do not ellipsize actions or hide a contradictory state below the visible content.

Launcher picker previews must match each variant's real layout and Halo theme. Use neutral sample content only in the picker/explicit configuration preview, labelled as preview where needed; sample data must never enter runtime projections, caches or briefs.

## In-app Screen dashboard

Register real clock/date, upcoming event, agenda, tasks, reminders, alarms/timers, weather, headlines, briefing, device status and quick-action cards. Reuse `ScreenWidgetCard` and its flat working-area presentation; add richer inner content only where justified by the card's actual size. Bind source/zone/filter configuration by stable presentation ID so two clocks or two selected feeds can coexist, and updates do not reorder the user's layout.

Normal use opens content. Deliberate Customize exposes move/resize/hide/configure with keyboard/accessibility alternatives to drag. Hide/removal changes presentation only; it does not delete a task, disable an alarm, deselect a source or erase its cache. Empty/unavailable cards offer the specific setup/recovery route. More rows belong in expanded cards or the canonical instrument, not nested tiny scroll areas. Keep the existing one-column large-text grid and ambient privacy/battery/thermal policy.

## Instance, privacy and result contract

1. **Durable independent configuration.** Store `appWidgetId`, provider/variant, schema/config version, selected owner IDs, zone/filter/ordered modules and disclosure preference. Editing uses a local draft with Save/Cancel and retains the original after cancellation. First setup cancelled means no completed instance. Missing sources after restore remain explicitly unavailable; never bind a substitute silently. Handle widget-ID remapping on host restore and delete only that instance's config on removal. Configuration is not a copy of organizer records or collector payloads. Android supports a configuration activity and reconfiguration of placed widgets; initial configuration must publish its completed widget explicitly. [Android configuration](https://developer.android.com/develop/ui/views/appwidgets/configuration)
2. **Exact action identity.** PendingIntent identity includes instance, action and relevant stable target/run/occurrence identity; extras alone are insufficient for isolation. Validate that the widget instance still exists, matches its current configuration and retains current authority before a mutation. Recheck Kids grants and Local/Power at execution, including stale cached clicks after profile/mode changes. Repainting and opening cached data perform no network work.
3. **Safe external disclosure.** Default external presentation is summary-only: no private titles, body text, addresses, note contents or child-sensitive details. Never place hidden data in accessibility descriptions, PendingIntent labels, preview images or device-protected caches. A locked/unknown host shows a neutral Open Halo affordance. Do not promise that a screen-lock broadcast can erase an already cached host view immediately. Android notes that some keyguard hosts do not require the keyguard category, so `home_screen` alone is not a privacy guarantee. Private-detail RemoteViews must not be published where lock-screen exposure cannot be excluded reliably; retain counts/approved summary and open authenticated Halo for details. [AppWidgetProviderInfo](https://developer.android.com/reference/android/appwidget/AppWidgetProviderInfo)
4. **One live authority.** Kids presentation uses the established shared-record/source bounds at projection time and click time; an adult-painted view cannot authorize a child action. Unknown profile/bootstrap/storage state stays safe and recoverable. Selection/clock/config edits remain useful in Local. Exactly Local and Power are displayed as global modes, never per-widget execution modes.
5. **Freshness is a fact.** Carry source label, observed/retrieved time, last success, expiry and current attempt outcome separately. Failed refresh retains readable cached information with stale/failed wording; it cannot reset the content timestamp. Use explicit Loading, No items, Choose source, Offline with saved data, Unavailable, and Retry later states. Show deferred refresh/backoff rather than pretending the tap fetched new data.
6. **Realistic clocks and delivery.** Prefer host-supported TextClock/Chronometer only for supported display behavior; they do not own alarms or prove a notification was delivered. Otherwise show a timestamped snapshot or stable end time. No app-driven every-second wake/poll loop, no wake lock for launcher animation, and no false “live” claim. Scheduled work and owner changes refresh cached projections within OS limits; a scheduler receipt remains the only source for delivery truth. `updatePeriodMillis` does not support intervals under 30 minutes. [Android widget updates](https://developer.android.com/develop/ui/views/appwidgets/advanced)

### W01 — P1: configuration recreation can silently rebase a stale draft

**Addressed in subsequently inspected source; tests pending.** The first `EverydayWidgetConfigurationActivity` kept `expected`, `loaded` and `instance` only in activity memory, while form fields used `rememberSaveable`. Recreating the activity after another editor saved reread the latest store version, then restored the older draft fields against that new CAS version. Save could overwrite the intervening edit.

The correction at `EverydayWidgetConfigurationActivity.kt:44–47,76–78` restores/saves the exact `EverydayWidgetReview` base, including its config/version, before any store reload. The form retains that reviewed version as its saved-state identity; the store comparison remains against the original version. Verify two editors, a concurrent save, recreation and a late Save: the stale draft must conflict, preserving both the current stored config and the unsaved reviewed draft. Also cover commit-before-result recreation without silently treating failure to finish the activity as failure to save.

### W02 — P2: recurring task cards use master dates and omit older overdue occurrences

**Open at first inspection; parent reports correction underway.** `EverydaySnapshotReader.kt:24–29` enumerated only today's midnight through the next seven days. `EverydayCards.kt:140–150` computed recurrence deadlines from that truncated set but displayed `recordRows` from the master record (`:108–109`). A completed/moved occurrence could therefore leave the original series date/title in the card, while an uncompleted occurrence before today disappeared from the overdue count. Repeating series with no remaining active occurrences could remain presented as an active actionable item.

Resolve actual incomplete occurrences, their override title/time and original identity for display/clicks. Bound the historical window deliberately and name that bound in the count rather than implying a complete overdue total. Acceptance: yesterday's incomplete occurrence, today's completed occurrence, a moved/renamed occurrence, and an exhausted finite recurrence; counts, displayed date/title and exact open target must agree. Parent's proposed past-30-day window and actual occurrence projection require matching source/test review.

### W03 — P2: initial/failed native faces have unreadable colors and hidden recovery

**Open; parent accepted.** `EverydayWidgetViews.unavailable` leaves XML colors `#183D35` / `#3F5D54` on the dark `halo_widget_background` fill `#12103E`, without applying the current scheme, reading scale or native Cyrillic layout. It sets a Configure label/click but never changes that view's XML `GONE` state. The same hard-coded colors/background occur in the initial layout and all inspected preview layouts, where no normal repaint supplies a corrected scheme.

Use a complete themed, bounded failure face with a visible named recovery action; ensure the initial/picker preview itself has readable foreground/background pairs before any worker runs. Test failed load at minimum size/200%, dark/light, Russian, high contrast and reapply from a previously populated widget. A generic Open Halo click is useful, but does not make an invisible Configure action usable.

### W04 — P2: live clock and announced/saved time diverge

**Open; parent accepted.** `EverydayWidgetViews.render` uses a live `TextClock` while the clickable root's content description includes fixed `face.value`, captured at the worker read. The date is another snapshot row. After a tick, assistive output can announce the previous time; locale-derived snapshot formatting can also disagree with the system's actual 12/24h choice. The renderer passes `snapshot.zone.id` even for “phone time zone”; an explicitly configured TextClock zone ignores subsequent system-zone changes until repaint.

Let the live clock own its current accessible time, use a live/date-aware representation or explicitly timestamp the date snapshot, and leave TextClock's zone unset when following the phone. Verify minute/date rollover and a device-zone/12–24h change without assuming a worker immediately runs. Avoid a parent content description that duplicates stale time or hides independently actionable rows.

### W05 — P1: an older worker can publish after a newer configuration or authority change

**Open; parent accepted.** `EverydayWidgetProvider.kt:55–70` reads an instance and snapshot, checks only the current Kids Boolean, then performs rendering and `updateAppWidget` without a publication generation/config-version fence or cancellation check. Replaced work has no suspension/check in that final loop. An older task can paint after a newer task saved/rendered a different configuration. Boolean equality also misses adult→Kids→adult transitions and sharing/source-approval changes within the same profile. Private row redaction reduces exposure but does not authorize stale adult headlines or outdated child-approved content.

Serialize/fence publication against the newest repaint generation and exact live instance/authority revision; revalidate after expensive rendering and before the host effect. Cancellation/removed-instance paths must not publish. Include terminal fallback updates in that ownership policy. Acceptance: hold old rendering, save/revoke/change profile, publish the new face, release the old render; the host must retain only the current authorized face and click payloads.

### W06 — P2: mixed-source cards can imply false freshness

**Open; parent accepted.** `EverydayCards.kt:166–176` combines articles from multiple sources but uses only the first article's source status/attribution/retrieval time for the whole face. A current source A and expired/failed source B can thus appear under a single “Saved snapshot is current” receipt. `DASHBOARD` at `:189–193` sets `observedAt=input.now` for a projection that did not retrieve anything; the Screen detail labels this value “Retrieved” (`HaloScreen.kt:779–781`). A freshly repainted dashboard can therefore imply that old source data was freshly retrieved.

Retain per-row source/freshness or compute an explicitly bounded aggregate that cannot describe stale rows as current. Keep render time distinct from retrieved/observed time. Also separate a selected weather source with no usable snapshot/failed first fetch (`weather():114–116`) from genuinely missing configuration; “Choose a saved weather source” is not recovery for an already correctly chosen source. Acceptance: fresh A + stale B, unchanged cached dashboard repaint, failed first weather fetch and selected-source removal.

### W07 — P2: configuration cannot express independent weather/headline modules

**Open; parent accepted.** The form's selected-source section initially includes CLOCK_WEATHER, HEADLINES and DASHBOARD, but omits the standalone WEATHER card. Two Screen weather cards consequently cannot choose their own saved cities through that form. Dashboard stores one weather `sourceId`; projection explicitly clears it for every non-weather section (`EverydayCards.kt:190`), so a Headlines module cannot retain a chosen source independently. The form also has no explicit ordered module editor; selection order is currently an incidental consequence of toggle order.

Expose a source choice for plain WEATHER and persist module-specific configuration and deliberate order for the dashboard. Preserve existing choices and invalid/unavailable IDs for review rather than silently adopting the first source. Acceptance: two weather cards with different sources plus a dashboard with different weather/headline selections; edit/recreate one without changing or rebinding another.

### W08 — P2: native measurement and bitmap sizing do not match rendered geometry

**Open; sent to parent.** `EverydayWidgetViews.kt:61–67` measures all text with Atkinson/Onest, but non-Russian title/value/clock XML uses Sora. It measures `face.value`, not necessarily the current TextClock's actual 12/24h text. The chosen fit can therefore disagree with the view the launcher renders. Separately, background width/height are clamped to 512 pixels (`:74,92`) while `nearbyBackground` still receives the original density and is stretched with `fitXY`: a 320dp-wide widget at 3× density stretches a 512px bitmap's 60px corner to approximately 37.5dp, instead of the intended 20dp. Different aspect ratios distort the outline/radius independently.

Measure the actual view font/style/clock format with the effective scale; reserve exactly the margins/targets that render. Bound bitmap memory while preserving its physical geometry, or use an equivalent supported background strategy. Verify 12/24h and long locales at 200%, narrow/default/expanded sizes, and high-density device-equivalent renders. Treat bitmap memory safety and Halo geometry as simultaneous requirements.

### W09 — P2: asynchronous widget entry has no retained/latest request owner

**Open; sent to parent.** `MainActivity.kt:331–348` removes every widget extra before launching a `lifecycleScope` resolver that can suspend during bootstrap/database reads. Activity recreation then cancels the resolver with no saved pending payload to consume. Separate incoming taps also start independent jobs; a delayed older resolution can write `requestedHaloScreen` after a newer request and open the wrong widget target.

Retain the immutable entry request until it is consumed or explicitly rejected and give the latest explicit request a generation/owner fence. Do not replay a consumed request after Back, and do not let an old error replace a newer successful navigation. Acceptance: block the first resolver, recreate the activity or deliver a second widget tap, then release it; exactly the current requested identity opens once with the older entry/draft preserved appropriately.

### W01 remaining — P1: a failed preference commit can still look completed in memory

`EverydayWidgetStore.kt:51–52` calls `SharedPreferences.Editor.commit()` after placing config plus completion in the editor, then throws on false. `completed():56–60` reads the same process preference cache. Android updates that in-memory map before reporting the disk-write result, so a failed write can still make the new receipt visible. Current activity finalization then remains busy; simply changing it to finish on any visible receipt would instead risk a false saved result. [Android SharedPreferences implementation](https://android.googlesource.com/platform/frameworks/base/+/d88b5baa7b5a/core/java/android/app/SharedPreferencesImpl.java)

Separate verified durable completion from failed/unknown persistence and restore or safely recover the previous durable configuration on write failure. Do not treat the cache value alone as proof after a failed commit. Inject a writer that updates its in-memory map but returns false; verify no false RESULT_OK, no permanent busy state and a recoverable prior configuration. This is a consequence of the new durable-receipt mechanism, not a request for unrelated storage refactoring.
