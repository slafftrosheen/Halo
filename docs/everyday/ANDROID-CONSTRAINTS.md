# Android implementation constraints

Research date: 1 November 2026. These are design constraints, not phone acceptance results.

Exact timing is reserved for user-requested alarms/timers and time-critical reminders. Check `canScheduleExactAlarms()` at scheduling time, expose the system grant route, and record the actual fallback. Android 14 fresh installs generally do not receive `SCHEDULE_EXACT_ALARM` automatically; restored records cannot imply a restored grant. Reconcile durable schedules after boot/time-zone changes and recheck permission immediately before each OS call. See [Android alarm guidance](https://developer.android.com/develop/background-work/services/alarms) and [exact alarm changes](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms).

Full-screen delivery is a separate special access on Android 14+. Only a real alarm delivery may request it; reminders, briefs and source updates do not. Check `NotificationManager.canUseFullScreenIntent()` and use a normal visible alarm notification when unavailable. Neither a saved record nor an exact-alarm grant proves notification/full-screen delivery. See [Android full-screen intent limits](https://source.android.com/docs/core/permissions/fsi-limits).

Launcher `updatePeriodMillis` cannot request refresh more often than 30 minutes. Use change-driven updates and bounded WorkManager refreshes; OS power restrictions can delay them. Widget projections must display actual successful data timestamps and never advertise an always-running exact clock. Existing `RemoteViews` rendering remains the platform adapter; per-instance settings belong to durable local storage. See [advanced widget updates](https://developer.android.com/develop/ui/views/appwidgets/advanced).

The organizer domain uses wall-clock dates plus named zones for recurrence, with explicit floating alarms when following device zone is requested. DST gaps shift forward by the gap; overlaps choose the earlier offset once. Monthly/yearly invalid dates are skipped, not clamped. Timers use elapsed realtime within the same boot and a persisted wall deadline after reboot. Those choices need user-visible time/zone/precision receipts and bounded host cases; OS background/Doze/permission/reboot behavior still needs the later authorized phone phase.

Before first unlock, credential-encrypted Room data is unavailable. Alarm recovery therefore needs a separately redacted, device-encrypted timing mirror and an Application startup path that does not initialize private storage or providers. Import locked-boot delivery outcomes only for the still-current record version after unlock. See [Android Direct Boot](https://developer.android.com/privacy-and-security/direct-boot) and the [Application lifecycle guidance](https://android-developers.googleblog.com/2016/04/developing-for-direct-boot.html). This is an implementation constraint; locked-boot acceptance remains for the later phone phase.

Reboot callbacks must not start a media-playback foreground service. The organizer adapter uses Android alarm notifications with bounded sound, rather than an application audio loop. See [foreground service start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start). Android notification/channel/DND settings still determine what a user hears.
