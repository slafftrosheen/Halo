# Everyday integration and recovery

Source checkpoint: 2 November 2026. Host verification is running against `integration-source.json`; this document does not grant hardware or participant acceptance.

## Existing owners and entry points

Organizer, Sources, World clocks and Your Day are first-party Screen instruments in the existing shell. Their content uses the current Material/Halo UI 5 color scheme, Sora/Atkinson (Onest for Russian), semantic labels, scalable text, native focus and the measured Halo Zone. The persistent Orb and labeled page actions remain shell-owned. The Library adds read-only references and instrument shortcuts, rather than copying organizer records into Notes or inventing another storage type. A Library reference rechecks the current record/version, source selection, child grant or brief visibility before opening its owner.

Related-item links retain typed identity: Notes use their canonical Workspace ID, organizer plans use `organizer:<id>`, Activity runs use `run:<id>`, and Timeline observations use `timeline:<presentationId>`. Removing a link removes no source record. Organizer change rows feed the existing Timeline projection with content-free action/version metadata. Activity can focus an exact run, object or observation; no second event bus or runtime is started by the collectors.

The optional Everyday stage in the existing setup journey offers language/category filters, saved metadata previews, explicit Power previews, cadence, offline city selection and initial Screen cards. Draft choices survive recreation/process restart. Saving source selection is local; external source fetching remains an explicit preview or the selected-source worker. Screen replacement uses its exact reviewed revision and the normal Undo owner. A successful save updates the page with its own committed versions, so a later adjustment does not conflict with its first save. An independent intervening change requires Reload and review. If source choices commit and Screen fails, the page describes that partial result and preserves the draft.

## Screen and launcher presentation

`EverydayCards` projects one typed face for both hosts. Screen supports independent stable card IDs, arrangement, size, archive/visibility, exact per-card configuration and persisted presets. The pre-existing device card keeps its canonical device owner. Screen configuration inherits the shell theme; native launcher instances can inherit the system or choose light/dark independently. Dashboard weather and headlines can select different sources, and module order is explicit.

Eight native providers cover clock/date, clock/weather, upcoming, tasks/reminders, brief, headlines, alarms/timers and dashboard. All use the same palettes, fonts and higher-contrast preference, opaque rounded surfaces, measured line heights, named Configure/Open actions and at least 48 dp actionable rows when the host size permits them. Large text is preserved rather than shrunk. Small hosts show a complete useful subset or an honest Open Halo/Configure face. Fixed-city clocks retain their zone and visible city; the phone clock follows time-zone changes. Android TextClock owns minute/date updates and live accessibility text. Data rows show saved observations and actual stale/error/retry status, without inventing a new retrieval time.

Each launcher instance has AtomicFile-backed configuration and independent PendingIntent identity. Compare-and-save uses its exact configuration version and an immutable operation receipt; rotation or a late paint failure cannot repeat the durable save. Family/mode/source authority is checked again immediately before publishing. Launcher faces suppress personal organizer/brief text even if an imported configuration requests otherwise; public source headlines remain attributed. Android and the launcher control placement, resizing and visibility, so Halo cannot promise lock-screen exclusion or placement acceptance.

Native data refresh is change-driven while Halo is alive plus a bounded 30-minute periodic worker, with boot/locale/time/theme recovery. Binding, scrolling, clock ticks and preview rendering never fetch. There is no per-second service, wake-lock loop or exact alarm for widget refreshing. Android battery restrictions can delay data refresh. The app does not describe timer widgets as continuously ticking.

## Portable data and retention

Brain archive version 5 adds checksummed chunked Everyday entries, with existing optional encryption and safety snapshots. Organizer records, authored recurrence exceptions, terminal delivery history, selected source metadata/cache, clocks, recent briefs/settings and Screen layouts/presets travel through the existing exporter/importer. Older archives remain readable. Native appWidget IDs/placements, active network jobs, OS permission grants and pending Android dispatch claims are not portable.

Restore validates size, nesting, typed payload/source agreement, IDs, parent graphs, exact occurrence identities and URLs before mutation. Domain restoration shares the existing Room transaction. Merge keeps local facts by default; explicit duplicates get new IDs with parent, related-organizer, Workspace and Screen selection remapping. Replace bumps versions above both incoming and pre-restore owners, including clock tombstones, to invalidate stale editors/intents. Running timers restore paused with remaining time; expired active timers become completed. Old revision cancellations cannot suppress a newer series. External restored sources start disabled for review, child grants clear, and proactive brief delivery remains off. Source retrieval timestamps survive restoration. Internal source cache is regenerated from canonical local owners.

Screen/settings publication follows the database commit. A disk or reconciliation failure in that phase is explicitly reported as data restored / remaining settings unfinished, never as an atomic rollback or a safe blanket Retry. The staged Apply plan is discarded to prevent another duplicate merge. Review the restored data/Screen or use the existing Undo restore safety snapshot. The importer does not silently replay a committed data phase.

Canonical organizer records remain until the user trashes and permanently removes them. Change history is bounded to 90 days; schedules/receipts are versioned. Sources retain one bounded typed snapshot and latest attempt until removal/cache clear; endpoint request budgets survive source removal for their rolling day and inactive retry metadata is pruned after seven days. Briefs, morning baselines and delivery history prune at publication after 30 days and the repository exposes at most 60 recent documents. Launcher operation receipts retain the last eight per instance. Setup drafts clear after a verified save; unfinished choices remain local. Existing full database clear/backup owners still govern this data; no Halo server is introduced.

Permanent Note purge clears matching derived local-source cache and saved briefs in the same purge transaction, changes the source authority token/version, and removes comparison baselines. A held collector cannot publish its old reservation afterward. Brief publication rechecks source versions and canonical Note existence inside its transaction, preventing a previously assembled excerpt from reappearing after purge.

## Provider disclosure and mode boundaries

The single global Local/Power choice remains serialized as the compatibility enum values PRIVATE/CLOUD. Power acknowledgment, category controls, parental restrictions, Android permissions and account authentication retain their existing owners; they are not alternate global modes. Local editing, deterministic brief assembly, offline cities and rendering need no model or server.

External collectors send only selected public URLs/validators or chosen weather coordinates and forecast parameters through the revocable public HTTPS transport. Preview uses the same transport budget. No Notes/organizer/notification bodies are attached to those requests. AI tools return only the invoked bounded result with Workspace provenance; clock/weather/location and activity/device categories are declared where applicable. Global Power does not expand a disabled context category. Tool schemas are closed and typed, writes use version checks and revocable foreground/family authority, and uncertain writes are never replayed. Structured Saved, Dispatched, Playback requested and Placement requested outcomes do not claim human-visible/audible completion.

## Acceptance boundary

Source implementation, host checks, rendered fixtures, installation, human use and actual Android behavior are separate evidence. Synthetic source titles in rendered tests are labeled fixtures. No host test establishes Xiaomi launcher placement, notification sound, Doze timing, permission-grant acceptance or assistive usability. The user requested the final build installed for their own testing; participant sessions remain deferred.

## Final privacy and compact-face corrections

Read-bearing tool outcomes and visible briefs carry a revocable in-process read admission, in addition to foreground/family/global-mode authority. Canonical source/sharing/organizer deletion edits and Note purge invalidate it inside their transaction; child project grant changes invalidate it at their existing local owner. The final disclosure also compares coherent canonical version/grant snapshots across the read, so a read beginning while a WAL writer is uncommitted cannot mistake its old snapshot for the new authority. Retrying a rejected read requires reading current state; an old grant is never treated as new permission.

Compact launcher fallback keeps its localized instrument identity and full static accessibility action. An Open label appears only when measured space permits; reading size is preserved. The eight variants therefore remain distinguishable at their supported minimum sizes. Status labels are generated from reviewed EN/RU/LV/PL sources. Native fixture clocks now use the same synthetic epoch as their saved-data fixture; configuration fixtures include the production Surface for meaningful dark contrast.
