# Intent and Execution Contract

This document defines the architectural boundary between the **Halo Cognitive Runtime** and physical/simulated **Embodiments** (e.g., BuddyBot, HeyCyan).

## 1. Intent Identity

Every intent generated by the Halo cognitive runtime is assigned a unique, immutable identity (`intentId`). 

- This ID MUST survive the entire end-to-end execution path.
- The embodiment (hardware/driver) MUST NOT generate its own identity for a commanded intent. It must use the provided `intentId`.
- Execution statuses and telemetry referencing a specific action MUST correlate using this `intentId`.

## 2. Embodiment Boundary

Halo is the cognitive side of the ecosystem; embodiments are the physical/actuating side.

- **Halo (Cognitive Runtime)**: Plans and decides *what* semantic actions need to happen (e.g., "move forward"). It produces a semantic `EmbodimentIntent`.
- **Embodiment Gateway**: The transport-agnostic interface in Halo that maps the semantic intent to device-specific or protocol-specific transports.
- **Physical Device**: Receives the raw commands, manages local safety, and executes the physical movement or actuation.

## 3. Capability Boundary

The cognitive runtime interacts with semantic **Capabilities** (e.g., `LocomotionCapability`, `CameraCapability`), not devices.

- A planner must NOT select a device based on connection state. It specifies the required capability.
- The `ExecutionEngine` resolves capabilities to the registered `EmbodimentGateway` capable of fulfilling it.
- If a device receives a command it cannot support, it MUST return a structured rejection, not silently ignore it.

## 4. Safety Authority

Safety is evaluated at the very edge of physical execution.

- The cognitive runtime proposes an intent.
- The physical embodiment's **SafetySupervisor** is the ultimate authority on whether that intent can be physically executed *at that exact moment*.
- Stale capability or authorization state MUST NOT bypass the `SafetySupervisor` evaluation immediately before execution.

## 5. ExecutionResult and ExecutionStatus

The lifecycle of an intent across the embodiment boundary is tracked via an `ExecutionResult` struct/class, containing at minimum:
- `intentId`: The unique intent ID.
- `status`: The current `ExecutionStatus`.
- `reason`: A textual reason for failures or denials.

### ExecutionStatus Semantics
- **CREATED**: The intent exists but has not entered dispatch.
- **DISPATCHED**: Handed off to the transport layer.
- **ACCEPTED**: The embodiment received and structurally validated the intent.
- **REJECTED**: The intent was malformed or unsupported.
- **RESOLVING**: The embodiment is resolving the intent into physical capabilities.
- **AUTHORIZED**: Execution is explicitly authorized by the safety supervisor.
- **DENIED**: Safety or policy prevented execution (e.g., obstacle detected).
- **EXECUTING**: The physical command is actively running.
- **SUCCEEDED**: The command completed successfully.
- **FAILED**: Execution was attempted but failed (e.g., motor error).
- **ABORTED**: Execution was intentionally interrupted.

*Note: Embodiments should only emit states they can genuinely establish (e.g., RESOLVING -> ACCEPTED -> SUCCEEDED/DENIED/FAILED).*

## 6. Device Identity

Devices are tracked via a compound `DeviceIdentity`:
- **Type**: The class of device (e.g., `BUDDYBOT`, `HEYCYAN`).
- **Instance ID**: A unique identifier for the specific device instance.

This allows Halo to correlate execution results and observations to the correct hardware without coupling the cognitive runtime to device-specific logic.
