# Halo roadmap to 10/10 usability and visual clarity

Date: 1 November 2026. Status: design and implementation proposal; the changes below are not implemented by this document.

Baseline: production UI at `aa53260fb645`, delivered on main in `df2d041f4b1e3307d4c715ee4a5bb5a6d678524b`. Independent expert review: usability 7.3/10 (29/40 Nielsen points), visual clarity 8.0/10, medium confidence. These are heuristic scores, not results from a representative user study. See the [review](../../testing/artifacts/HALO-ZONE5-DEVICE-POLISH-2026-11-01/UX-ANALYSIS.md) and [current workspace contract](WORKSPACE-TOOL-CONTRACT.md).

## 1. Product goal and definition of 10/10

Halo should let a person understand where they are, choose a useful action, see what happened, recover safely and continue their work. Confidence, reading ability, vision, dexterity, language and experience matter alongside age. We should test those needs separately rather than assume every child needs the same help or every older person needs a simplified app.

The target is one coherent product with optional guidance, comfortable presentation and efficient shortcuts. The five instrument families and the Halo identity remain stable. Kids retains its restricted capabilities and parent boundaries.

A 10/10 result must be earned against a declared scope of supported tasks and users. Keep the existing scoring scales: all ten usability heuristics at 4/4 and all five visual dimensions at 2/2, assessed independently with evidence. Do not manufacture progress by changing the scale or predicting scores before testing. Shipped capabilities define the scope; a calendar or alarm that is not implemented cannot be counted as a successful task.

Proposed release targets below are Halo product goals, not universal standards or measurements already achieved:

| Measure | Target and interpretation |
|---|---|
| First-use completion | At least 95% observed unassisted completion of supported essential tasks within each tested user group in validation; report raw counts and uncertainty. Small formative rounds cannot establish a population rate. |
| Repeat use | At least 98% observed completion of the same essential tasks after familiarisation; report separately by group and task. |
| Task ease | Median at least 6/7 in each group, with low ratings investigated individually. |
| Responsiveness | Starting target: at least 95% of local control activations receive visible acknowledgement within 100ms on declared test devices. Measure it; animation duration is a separate property. Long operations immediately expose their real state and cancellation where supported. |
| Understanding | People can explain the page purpose, current object and next action without a tutorial; at least 90% observed correct identification in validation. |
| Safety | Zero observed lost-work, unintended external-action or child-boundary failures in the required scenario matrix. Any such failure blocks acceptance, regardless of the numerical score. |
| Recovery | Every deliberately introduced supported failure has a working recovery path; users retain recoverable input and can understand the result. |
| Accessibility | Essential tasks work with touch, large text and supported assistive input. No critical operation depends exclusively on a hidden gesture or voice. |
| Visual clarity | No clipped essential label, ambiguous primary action, colour-only distinction or unverified core state in the supported matrix. |

These goals measure supported users and scenarios. They are not a promise that one study can prove effortless use for every individual.

Before counting results, define the task actor, required capability profile, permitted support and durable completion criterion. “Unassisted” means no facilitator instruction; assistive technology and the product's own available Help remain permitted and their use is recorded. First use means no prior Halo experience. Repeat use follows one documented practice loop for that instrument; record learning time and test later return separately.

Learner-only tasks and child–caregiver tasks are separate. A child correctly requesting the intended caregiver authentication is successful handoff, not failed independence. A paired task finishes only after the authorised caregiver flow reaches its expected result. Unsupported tasks cannot silently disappear from the denominator: record them as capability gaps outside that profile's successful-use claim. A failed task and successful recovery are reported as two outcomes; recovery does not erase the original failure.

## 2. Preserve the Halo contract

- Normal portrait: upper 75% is working content, lower 25% is the Halo Zone, measured after safe system insets.
- File identity, truthful status, navigation and permanent command controls live in the Zone. Selection handles, text carets and document manipulation are working content. Temporary inspectors open deliberately from the Zone or a selected object.
- Settings, keyboard and short windows use the compact row. Large-text/narrow layouts retain the accessible fallback; focused content remains reachable.
- Android Back owns return navigation. Do not restore duplicate Back buttons in the Zone. Back closes the keyboard or temporary interaction before leaving the appropriate work context, following Android and the current editor owner.
- New capabilities are instruments within HaloStudio, HaloNotes, HaloStudy, HaloMemory or HaloCanvas. Screen owns its calendar, plans, weather, clock and alarms. No new top-level tool for every feature.
- Retain the approved thick open-ring orb, its glow character, supplied assets and reactive semantic themes. Design proposals extend this language.
- Kids follows the same placement and visual grammar with its permitted actions. Presentation preferences never grant adult, provider, source, sharing or parent authority.

## 3. Styling and visual grammar

### Hierarchy

Give every working page one obvious starting action. A new graphics project points toward adding content; an existing note points toward editing; a failed export points toward recovery. Primary, secondary and destructive controls have distinct treatments. The whole page must not glow or compete for attention.

Keep three stable visual layers: quiet workspace background, readable content surfaces, and the command/status Zone. Reserve stronger accent, fill and weight for selection, the principal action and deliberate guidance. Use spacing and headings to group related controls before adding more boxes or dividers.

### Typography and layout

Use shared text roles rather than per-page sizes. Initial prototype ranges: 16–18sp reading text, 14–16sp action labels and readable secondary metadata. Essential meaning must not rely on tiny metadata. Validate actual font metrics and line heights in EN/RU/LV/PL and every other advertised language. At 200% text, reflow and scrolling preserve full labels and focused controls.

Preserve the existing 12dp control, 20dp card and 26dp hero shape family unless a reviewed prototype establishes a better fit. Use a small shared spacing scale, initially 4/8/12/16/24dp. Icon strokes, visual weight and alignment should match the native Zone 5 family; avoid mixing thin and heavy substitutes for equivalent functions.

Android recommends at least 48dp interactive targets. Halo should prefer 56dp for frequent controls where the measured layout permits it, retain at least 56dp for tested child controls, and maintain the 48dp adult floor. Interactive bounds must not overlap. Larger targets must not be obtained by shrinking labels or expanding invisible hit areas across adjacent controls. [Android Compose accessibility](https://developer.android.com/develop/ui/compose/accessibility/api-defaults).

The quarter-height layout has a finite budget. Prototype the orb caption, metadata, menus and accessible targets together on the smallest supported normal window. If space is insufficient, move secondary commands into the existing grouped action sheet. Never add a permanent row above the work area or silently exceed the quarter-height allocation.

Initial layout budgets below are prototype constraints at nominal text size, not measurements of a delivered caption design. The current 14sp action-label role has a 19sp line height, so allow 20dp for a single-line caption at nominal scaling rather than treating font size as line height. Heights include the complete Zone rectangle, spacing and a 1dp divider. Actual localised text, side labels and nonlinear scaling determine the final measured layout.

| Configuration | Proposed allocation | Fallback and acceptance |
|---|---|---|
| Redmi reference: usable 791.3dp; normal Zone 197.8dp | Adult editor: identity/status and trailing controls 56dp + menu row 48dp + central 64dp orb/20dp caption slot 84dp + spacing 8dp + divider 1dp = 197dp | No extra hint row. Frequent adult controls prefer 56dp; menu targets retain the 48dp floor. This leaves less than 1dp spare: any measured overflow triggers the fallback, not compressed text or targets. |
| Child normal reference | Noninteractive identity/status summary 48dp + child action strip 56dp + orb/caption 84dp + spacing 8dp + divider 1dp = 197dp | Prototype horizontal labelled Type/Help controls to fit the 56dp strip; this is not a claim that the current vertical satellites already fit. Interactive targets stay at least 56dp. Applicable child editor groups use the same measured fit rule; rename or other actions use real menu entries rather than undersized metadata hotspots. |
| Smallest current normal-height boundary: usable 520dp; Zone 130dp | One-line noninteractive summary 28dp + orb/caption 84dp + spacing 8dp + divider 1dp = 121dp | File/Edit/Add/View/More and trailing secondary controls move to grouped Actions. If the measured summary exceeds the remaining 37dp or labels grow, move the summary there too. Prioritise current task state in visible wording; full identity/status stays reachable in Actions. No tiny targets or utility scrolling to discover the main action. |
| Compact Settings/IME/short window | Adult starting budget: 48dp visual orb + caption 20dp + spacing 8dp + divider 1dp = 77dp; child: 56dp + 20dp + 8dp + 1dp = 85dp | One horizontal control row containing the orb/caption unit. Global Menu and local Actions keep their targets; identity/status and secondary menus move into Actions. Measure all side labels and insets; use the largest required control height. |
| 200% text or narrow width | Height follows measured caption/side-label wrapping; retain the supported content-sized accessibility fallback | No target/text shrink, overlap or essential ellipsis. Short visible action wording has a full accessible label/state. Verify the usable work area on the shortest supported window. |

Use a measured fit rule: when identity + applicable menus + navigation/caption + spacing + divider exceed the normal quarter budget, move the secondary menus and trailing shortcuts into Actions, followed by the noninteractive summary if necessary. The normal Zone itself remains exactly one quarter. The numerical examples do not cover 200% text: the documented accessibility fallback follows measured text and targets without shrinking either. Full identity/status and commands stay reachable, and urgent task state cannot disappear solely to make the budget fit.

Separate the text editor/composer task surface from compact navigation measurement. Gate the full Zone rectangle rather than merely checking that three navigation buttons share a baseline. Preserve the Home composer's single focus/draft owner through any placement change. The keyboard must not cause a second permanent command row or a lost draft.

### Colour, files and state

Tools retain accent-led symbols; files retain a distinguishable companion ink, document/type shape and visible type/name. Selection also uses a check or border, so colour is supplementary. Error, warning and success use consistent semantic roles across all palettes.

Adopt at least 4.5:1 for ordinary text and 3:1 for essential non-text UI against its actual adjacent surface; aim higher for long reading and important status. Check wallpaper underlays, pressed/selected states and disabled explanations, not just a base colour swatch. These are accessibility targets; passing a sampled screenshot is not complete certification. [W3C text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [W3C non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).

Test every advertised accent/tone, light/dark, high-contrast and background combination. A palette change repaints semantic UI and orb together. Stored artwork, document colours and ink retain their content meaning.

## 4. Navigation and commands

Keep a clear distinction between global Menu and local Actions. Global navigation changes destination. Local Actions operates on the current document or task. Search results and shortcuts must name their destination or affected object.

Within the five instrument families, replace the compact flat action list with the same applicable File/Edit/Add/View/More groups used in the normal Zone. Keep their order and meanings consistent. Other surfaces need meaningful local groups: Home uses conversation/attachments/history; Screen uses its supported cards/layout/daily tools; Settings uses preference search/sections/help; Devices uses connection/management/help; Activities uses review/history/filtering. Kids keeps its permitted Type/Help/Stop/parent commands. Do not impose file menus on a surface without file operations.

Add scoped command search when command volume justifies it, useful synonyms and clear unavailable reasons. Show current status once. Common actions appear near the top of their group; less common actions remain reachable without guessing an icon.

The orb needs a visible action caption, such as Talk, Send, Stop or Review, derived from its real callback. Keep the activity state distinct: “Listening” describes what is happening; “Send” or “Stop” describes the next tap. Present activity in the existing status area or a compact combined phrase where needed, with full accessible action/state semantics. Its central slot remains stable. Caption placement must fit the normal Zone and compact row without shrinking the orb's recognisable geometry, removing typing access or causing overlap. Long press and upward swipe remain optional menu shortcuts with visible equivalents.

Preserve the user's location: Library filter, sort, scroll position, selected item, tool subview and relevant document position. Returning from an editor should restore the originating context and make the edited object easy to locate. Opening a file chooses its supported editor from canonical type metadata; the user should not repeatedly choose its tool.

Home and HaloScreen need more obvious purpose labels. First use the existing names with clear descriptions such as “Talk to Halo” and “Your day”. Test alternative visible labels before adopting a rename; retain internal routes and compatibility IDs. Similarly, remove inconsistent Office/Notebook/File tools wording from visible places where HaloNotes is the correct family.

Prototype a clearly grouped Workspace section in the adult Menu to improve direct instrument access. This group, its search results and pinned shortcuts must stay outside the child allowlist; child navigation remains Home/Study and explicitly permitted child-owned destinations. Choose its final form through first-use tests. Assess success, hesitation and backtracking alongside tap counts; an extra obvious step can be easier than a crowded menu.

Initial efficiency goals: a family remains two deliberate selections from Workspace Library; a selected object's relevant properties are reachable in no more than two command selections, plus an explicit Apply when necessary. Export and save should not require a detour into another family. Record input, scrolling and system pickers separately when comparing paths.

## 5. Trust, saving and recovery

This is the first implementation priority. Replace generic “something went wrong” states with operation-specific outcomes: save, import, export, restore, permission, source change, offline and unavailable capability. The user sees what happened, whether work is safe and a relevant next action. Internal exception text stays out of the UI.

Example: “The export could not be written to that folder. Your project is still saved on this phone.” Actions: Choose folder / Try again. The safety sentence is shown only when a durable project receipt supports it. An unknown result must remain unknown until checked.

Use consistent vocabulary while retaining each instrument's real storage semantics:

| State | Meaning |
|---|---|
| Editing / unsaved | The current change has not yet reached the relevant durable owner. |
| Draft kept on this phone | Recoverable local edits are durably present. This does not imply an exported file or cloud copy. |
| Saved | The named document/project version is committed through its real owner. Explain explicit version/checkpoint semantics where applicable. |
| Exported copy | A separate output has been created and verified. Show its real location or opening action. |
| Waiting / needs review | Work or approval is still pending; the interface cannot imply completion. |
| Failed / cancelled / unknown | Distinct outcomes with appropriate recovery and preserved context. |

Back, orientation change, backgrounding, process recreation and interrupted operations must preserve what their canonical owners promise. Check startup and resume: persisted locale/appearance and restored context should be ready before interactive controls can change meaning or position; defer heavy optional initialisation so it does not freeze local navigation. Avoid unnecessary confirmation dialogs for reversible local operations; offer working Undo where supported. Irreversible or external operations retain their existing confirmation and authority boundaries.

## 6. Fluent instrument workflows

The common pattern is Open/Create → Work → Inspect/Adjust → Keep/Save → Export/Continue. Each family uses the same placement, selection vocabulary, temporary inspector behaviour and recovery grammar.

| Surface | Roadmap outcome | Essential scenario |
|---|---|---|
| Home | Clear optional Talk/Type entry, visible capture state, honest review/results and accessible Stop | Type a request, cancel safely, resume without losing the draft; optional voice with explicit consent and state |
| Library | Recognisable file rows, search/filter clarity, useful recent work, consistent selection and return position | Find an unfamiliar saved item, open the right editor, return and identify it |
| HaloNotes | Writing first; formatting, structure and supported document operations grouped consistently | Create/edit text, insert supported content, close/reopen, export a supported format |
| HaloStudio | Artboard first; selection opens appropriate properties, consistent layers, undo and manual creation | Import an image, add text/shape, adjust a selected layer, undo, save/reopen and export |
| HaloStudy | Sources → learning goal → activity → review; one clear next learning action | Start from chosen material, understand the source, ask for help, resume and finish a learning step |
| HaloMemory | Clear distinction between a saved source and remembered context; scope/source visible | Review a fact, correct it, or forget context while understanding what happens to its source file |
| HaloCanvas | Add linked material, connect/group it and understand its relationship to source files | Combine a note and image, connect ideas, open the source and return without losing the board |
| Kids | Picture/word/spoken support for permitted tasks; predictable Type/Help/Stop and parent boundary | Learn or create manually, ask for help, keep work and return safely within a real Kids session |
| HaloScreen | Clear, truthful status for existing daily-life tools and permission/setup needs | Read a supported card and understand whether its data/action is available |
| Devices / Activities / Settings | The same state, grouping, colour and recovery language | Understand connection state, review a pending action, change and persist an appearance preference |

Studio gets a consistent inspector and layer vocabulary. Direct object selection is working content; permanent toolbars remain in the Zone. Provide accessible property controls for manipulation and alternatives to critical pinch/drag/long-press actions. Manual work stays first, and AI actions stay deliberate and secondary.

The Android file handoff is part of the workflow: start in Android Files or a supported source app → Open with/import into Halo → recognise the type and retain the granted source access → edit → choose a supported export destination → verify and locate/reopen the output → return to the same Halo context. Also cancel the picker, revoke folder access, background the app while choosing, and return after another app opens the result. Unsupported intent entry points, formats or destination operations are explicit capability work, not navigation polish or delivered features.

Cross-family “Continue in…” and “Add to canvas” commands should reuse actual compatible source/version owners. Explain whether the result is a link, a copy or a new output. Do not claim format support, live linking or editing capability that the backend does not provide.

Screen's owned calendar/plans/weather/clock/alarms need separate functional delivery: storage, scheduling, permissions, notifications, reliable state and recovery. They inherit this UI contract when genuinely supported. Existing unavailable projections remain honest.

## 7. Hint and learning system

Use a deterministic, local presentation state machine over real current actions. It does not require an AI request or private content inspection.

| Level | When it appears | Behaviour |
|---|---|---|
| Clear default | Always | Visible action words, sensible starting state, meaningful empty state and current status |
| Quiet cue | A known safe next step is available and the user is idle | One halo trace around the actual labelled control; no layout movement |
| Short explanation | Guidance is enabled and measured space permits | One short phrase, such as “Add text or an image”; it never replaces file identity/status |
| Explain this step | The user asks for help | Temporary task-focused explanation with an example, a clear next action and optional spoken reading |
| Guided task | Explicitly selected by the user | One step at a time, preserving work and allowing pause/exit; all commands use the same real owners |

Use a branching presentation model, not a compulsory tutorial sequence:

- Idle becomes Eligible only when a safe, live candidate exists; an idle delay may then show its Quiet cue.
- An Eligible or Cued step may show a short proactive explanation only when preferences and measured space permit. Requested Help or a Guided task is another branch, not a prerequisite for completion.
- The user may complete or dismiss the step from its cue, explanation or requested Help without opening another help level. Completion follows the actual goal confirmed by its real owner: adding a layer requires a successful Apply/result, not merely opening Add. Where the goal promises kept work, the durable receipt is required.
- Page/object/version changes or blocked interaction invalidate the presentation and return it to Idle without inventing completion. Evaluate a confirmed goal result before discarding its old presentation version; invoking a callback alone is not success.
- Closing requested Help returns to the unchanged task without immediately reopening its cue. Dismissed versions remain suppressed; help stays available on request.

Only one target is guided at a time. The target must still be visible, enabled and bound to the current entry/object/version. Recheck eligibility on selection, navigation, source or permission changes. A cue must never dispatch an operation or grant authority.

Suppress proactive hints during typing, recording, speaking, busy work, recovery, menus, inspectors, review and parent disclosure. After dismissal/completion, remember the hint version locally; reopening the app is not a reason to repeat it. Let the user ask again or turn guidance off.

Keep words concrete: “Add a photo” rather than “Populate your workspace”. Do not nudge destructive actions, parent unlocking, paid work, provider setup or external sharing merely because the user is idle. Help for these boundaries explains a user-requested action without pushing consent.

A nonessential helper may use the current six-second default, adjusted for Android accessibility timing. User-requested instructions stay until dismissed. Essential status, errors and recovery are never readable only through a short-lived tooltip. Clear language and separated instructions follow cognitive accessibility guidance. [W3C clear content](https://www.w3.org/WAI/WCAG2/supplemental/objectives/o3-clear-content/).

Example: a beginner creates a Studio project. The empty artboard explains its purpose; the existing Add control receives one trace. Choosing Text opens the real text inspector and pauses coaching. After Apply, a verified draft state replaces uncertainty. Export guidance appears when the person chooses to make an output. An experienced user can dismiss coaching, use the same Add group or scoped search, and reach the same owner without a separate workflow.

## 8. Motion, halo FX and wallpapers

Every effect needs a purpose: show an accepted touch, preserve spatial continuity, expose a real state, guide one action, or acknowledge a verified result. Core controls remain usable while transitions run.

The following timings are starting values for prototypes, not requirements from an external standard:

| Effect | Proposed behaviour |
|---|---|
| Press feedback | Approximately 60–100ms; clear touch acknowledgement without scaling text into blur |
| Selection/state change | Approximately 150–220ms; stable geometry and persistent selected shape/label |
| Sheet/inspector | Approximately 220–300ms; predictable origin and focus restoration, interruptible by Back |
| Next-step halo | One restrained 700–1000ms lap, then a quiet static cue; no repeating beacon on every button |
| Orb idle | Brief arrival/settle, then still; retain the thick ring/glow character |
| Listening/thinking/acting/speaking | Actual runtime state, visible words and accessible Stop; indeterminate motion never implies completed work |
| Success | One short 250–400ms acknowledgement after a real receipt; persistent truthful result remains |
| Error | Stable icon/text and matching recovery; avoid shaking, flashing or decorative drama |
| Wallpaper | Very slow, small drift; initial full-cycle range 120–240 seconds, about 1–2% translation; no interaction or reflow |

Allow at most one attention-seeking cue at a time. Real task feedback and user-controlled interaction take priority over guidance and ambient decoration.

Reduced motion removes nonessential movement while preserving all information through labels/shapes. Higher contrast can remove decorative glow and wallpaper. Respect foreground, power and thermal gates; a paused animation must not imply the underlying operation stopped. Provide a still background choice and a direct motion preference. The product adopts stronger comfort behaviour where appropriate; WCAG's interaction-animation criterion is Level AAA, not an AA requirement. [W3C animation guidance](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html).

Measure actual dropped frames, input latency and motion on low/mid-range phones; a two-frame wallpaper difference is insufficient. Inspect rendering with more than one capture path because the Redmi fixture evidence exposed incremental screenshot anomalies. Confirm an observed defect on the real display before changing production paint.

## 9. Broad age, ability and experience support

Offer independent controls for help amount, text size, contrast and motion. Experienced users can reduce coaching, use scoped command search and deliberately pin frequent commands within the existing space budget. Core commands retain stable locations; usage prediction must not reorder them unexpectedly.

Guided presentation uses larger comfortable choices, plain language, explicit next steps and optional reading. It is available to adults as well as children. Do not label it “senior mode” or assume that age predicts technical skill.

Kids keeps its parent-managed content, sharing, source and provider rules. Optional read-aloud must not duplicate TalkBack speech or start a microphone. Test the existing pre-reader first-tap-read/second-tap-choose interaction against alternatives with actual pre-readers and caregivers before changing it; preserve the current TalkBack interaction model.

All essential tasks need readable text and non-colour cues. Test TalkBack order, labels, selected state, errors, custom actions and return focus; Switch Access; external keyboard; magnification; one-handed use; and comfortable target separation. Focused input and controls should stay fully visible above the keyboard/sheets, which is a stronger product goal than the WCAG AA partial-visibility minimum. [W3C focus guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).

Use Android text units and real system scaling rather than multiplying every dimension manually. Android supports nonlinear font scaling to 200%; test maximum system font, narrow windows and localised strings. Canvas/artwork zoom is a separate concern from the size of its editing controls. [Android font scaling](https://developer.android.com/about/versions/14/features#non-linear-font-scaling).

## 10. Delivery order

Each batch includes accessibility, localisation, Kids parity where permitted, honest states and regression checks. These are not a final coat of polish. Sizes are relative: M = shared multi-page change; L = domain workflows/persistence or research across groups. Estimate calendar duration after Batch 0 confirms scope and team capacity.

| Batch | Priority / size | Deliverables | Exit condition |
|---|---|---|---|
| 0. Establish the baseline | First / M | Supported-task inventory; flow/state map; consistent terminology; participant plan; baseline observations; prototype decisions | We can name each shipped task, owner, success/recovery state and missing evidence; prior scores retain their original meaning |
| 1. Make work trustworthy | Highest / L | Operation-specific recovery; saved/draft/export grammar; Back/reopen and interrupted-operation handling | Required failure scenarios recover with correct state and zero observed lost work; no false success or authority bypass |
| 2. Make the shared shell obvious | High / M | Visible orb action; grouped compact Actions; clear global/local navigation; retained context; shared typography/colour/target rules | First-use recognition improves; quarter-height and compact/200% layouts pass with no lost command or overlap |
| 3. Complete the main work loops | High / L | Real create/edit/inspect/save/reopen/export/continue scenarios across families; a complete real Kids session | Participants can finish the supported tasks; manual graphics/text flows are clear; source/version and parent boundaries remain correct |
| 4. Teach at the right moment | High / M | Layered hints; explicit guided tasks; optional reading; dismissal/preferences; useful empty states | New users discover the next action, can dismiss help, and complete tasks without coaching interference or automatic execution |
| 5. Refine motion and comfort | Medium / M | Motion tokens; classic orb state parity; restrained wallpaper; reduced-motion/contrast/performance checks | State remains understandable with motion off; interaction stays responsive; no competing effects or persistent distraction |
| 6. Validate and iterate | Required / L | Repeated real-user rounds, independent rubric review, actual device/assistive checks and regression evidence | No unresolved core task or severe issue; score and product targets meet the declared scope with evidence and uncertainty reported |

Run small usability rounds during the earlier batches; Batch 6 is the final cross-group validation, not the first time users see the design. Do not start a new visual direction while the shared placement/terminology is still changing.

## 11. Testing programme and acceptance matrix

Recruit for different needs: pre-readers with caregivers; reading-age children; teenagers; adult phone novices; experienced creators; older adults with mixed experience; and people using assistive technology or living with low vision/dexterity/cognitive needs. These overlap; age bands alone are insufficient. Agree child participation and research consent with caregivers, use appropriate tasks and allow stopping.

Begin with small moderated rounds, roughly 6–8 people for each selected need/experience pattern across iterations. Use neutral task descriptions and synthetic files, not a tutorial telling users which buttons to press. Small rounds reveal issues; size a separate validation study when a reliable population-level rate is required.

Observe first attempt and repeat use separately. Record completion, help requests, wrong destinations, backtracking, destructive slips, recovery, time, ease and what the person believes happened. Separate task time from provider/network waiting. Report raw counts by task and group, medians/ranges and uncertainty; repeated tasks from one person are not independent participants. Content-free local diagnostics can support the study. Shipping new analytics is a separate consent/ownership decision.

Define capability profiles before selecting scenarios:

| Profile | Eligible scenarios and expected outcomes |
|---|---|
| Local/manual | Supported editing, saved files, local export and other operations that genuinely need no provider. New model-dependent lessons are included only if an appropriate local runtime is actually available. |
| Provider-enabled | Deliberately configured and authorised model-dependent work, including correct dispatch, results, interruption and recovery. Record latency and failures as part of the end-to-end experience. |
| Offline/unavailable | Recognise the limitation, retain work, use an actual manual alternative or recover/exit safely. Do not count a nonexistent offline capability as a success. |
| Child-restricted | Learner-only tasks under current child rules, plus separate paired caregiver tasks where authentication/sharing authority is genuinely required. |

Different participant groups receive relevant tasks from these profiles, not an identical adult feature list. Provider/network waiting is measured separately for diagnosis but remains in end-to-end task reporting; failed provider work remains failed work.

Required task set:

1. Understand Home versus Screen versus Workspace and choose the right starting place.
2. Find a saved file, recognise its kind, open it, edit and return to the same Library context.
3. Create and reopen a note; use a supported export and find the real output. Also open/import an eligible file from Android Files, cancel its picker, choose a supported destination, reopen the output externally and return to Halo.
4. Create a manual Studio composition, adjust a layer, undo, save/reopen and export.
5. Recover from lost folder access, unavailable source, failed export and interrupted save without believing work is lost or complete incorrectly.
6. Start learning from selected material, ask for help and resume a lesson.
7. Correct or forget remembered context while understanding the source-file result.
8. Combine and reopen source material in Canvas, distinguishing links from copies.
9. Complete a real permitted Kids learning and manual-creation flow; verify typing, help, Back, kept work and parent gate through their actual owners.
10. Use essential tasks with TalkBack or supported assistive input and with 200% system text.
11. Change theme, background and guidance preferences; restart and verify persistence in the active and inactive appearance profiles.
12. Cancel optional voice/AI work and continue with touch or typing without being stranded.

Test states include new/empty/populated, loading, busy, offline, unavailable, failure, cancellation, unknown outcome and recovered state. Required configurations include normal/narrow/short landscape, keyboard, large text, light/dark accents, higher contrast, motion off, power/thermal restrictions and supported languages. Capture each device's current preferences before that QA session and restore that snapshot; do not substitute an older session's baseline.

Use separate matrices for automation and participant studies. Exhaustively check finite semantic colour-role combinations and action-state rules where practical. Use representative rendered screen/layout combinations plus risk-based extremes rather than claim every possible Cartesian combination was photographed. Participant sessions use a balanced, relevant subset; specialist accessibility and device checks cover their specific risks. No demographic group has to repeat every palette and window configuration.

Automated tests cover owners, leases, state transitions, persistence and layout. Native-renderer fixtures cover controlled paint/geometry. Full-app physical journeys cover real navigation, editing, files and system UI. Real participant and assistive tests cover comprehension and operation. Evidence at one layer cannot silently substitute for another.

## 12. How the scores reach their targets

| Usability dimension | Current /4 | Target evidence for 4/4 |
|---|---:|---|
| System status | 3 | People correctly distinguish draft, saved, exported, pending and unknown results |
| Real-world match | 3 | People choose the right family/page from plain names and purpose labels |
| Control and freedom | 3 | Cancel, Back, Undo and reopen work through real persistence owners |

## 13. Prototype decisions before implementation

| Decision | Recommended direction | What must be demonstrated |
|---|---|---|
| Home / Screen naming | Keep identity and add literal purpose labels first; test any rename | People distinguish conversation, daily tools and file work without a tour |
| Orb caption | A short visible action caption with separate activity status within the existing Zone layout | Recognisable classic orb, readable text, typing/menu access and measured height all survive |
| Compact commands | Shared grouped Actions, with scoped search when needed | Faster finding and less scanning across novice/expert and large-text users |
| Direct family access | Prototype an adult Workspace group within Menu | Clear hierarchy and orientation without overwhelming the menu or exposing adult destinations in Kids |
| Pre-reader choices | Validate the current interaction and compare a clear alternative | Children understand choosing versus hearing; TalkBack and parent controls remain correct |
| Experience preferences | Independent guidance/text/contrast/motion controls; optional expert shortcuts | People gain comfort or speed without losing familiar commands or permissions |

These are reviewable design proposals. Substantial departures from the approved visual language or visible names should be agreed with the user before application.

## 14. Implementation starting points and first deliverable

Shared shell work belongs in `ui/shell/HaloZone.kt`, `ui/presence/HaloZone5OrbLauncher.kt`, `ShellPageActions.kt`, `ui/zone5/WorkspaceToolMenus.kt` and `Zone5Guidance.kt`. Styling uses the existing theme/design tokens and artwork mapper. Recovery begins with Studio's operation/state model, then extends the common outcome language to the other actual owners. Kids continues through its existing scoped binding, Back owner and credential gate.

Do not introduce another command registry or execution path for hints/search/shortcuts. They remain presentation over the current live action lease. Source/object/version, permission, confirmation and durable-result authority stay in their canonical owners.

The recommended first implementation package is: typed Studio recovery, one saved/draft/export vocabulary, a prototype of labelled orb plus grouped compact Actions, and actual save/Back/reopen/export tests in Studio and Notes. Review that package before expanding the same grammar across all families. This addresses the current weakest scored areas and creates reliable flows for later guidance and motion work.
